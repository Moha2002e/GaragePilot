2. OBJECTIF DU PRODUIT
----------------------

GaragePilot est un SaaS de gestion destiné aux petits garages automobiles
indépendants en Belgique.

Promesse produit :

« Toute la gestion du garage, de l'entrée du véhicule jusqu'au paiement, sans
encoder plusieurs fois les mêmes informations. »

Parcours final attendu :

Création du garage
  -> connexion
  -> création du client
  -> ajout du véhicule
  -> création du rendez-vous
  -> création de l'intervention
  -> ajout des travaux, pièces et heures
  -> création du devis
  -> acceptation ou refus du devis
  -> fin de l'intervention
  -> création de la facture
  -> ajout des paiements
  -> facture payée

GaragePilot doit rester simple, rapide, lisible sur ordinateur et tablette,
et utilisable sur téléphone pour les actions d'atelier essentielles.

4. PRINCIPES D'ARCHITECTURE
---------------------------

GaragePilot commence comme un monolithe modulaire. Il ne faut pas introduire de
microservices, Kafka, CQRS ou Event Sourcing sans nécessité réelle.

Le backend est organisé par couches globales, conformément au choix du
propriétaire du projet :

backend/src/main/java/be/garagepilot/
  controller/   contrôleurs REST uniquement
  service/      logique métier
  repository/   accès JPA aux données
  model/        toutes les entités et énumérations métier
  dto/          objets d'entrée et de sortie de l'API
  mapper/       conversion entités vers DTO
  security/     JWT et utilisateur connecté
  config/       configuration Spring/Security
  exception/    exceptions et gestion globale des erreurs

Exemples : ClientController, ClientService, ClientRepository, Client et les DTO
ClientRequest/ClientResponse. La même structure doit être respectée pour les
véhicules, factures, rendez-vous, atelier, devis et futurs modules.

Le nom métier retenu dans le code est « Client », et non « Customer ».

Le frontend est organisé avec :

GaregePilotFront/src/app/
  core/models/       modèles TypeScript partagés
  core/services/     appels API partagés
  core/guards/       protection des routes
  core/interceptors/ ajout automatique du JWT
  layout/            structure sidebar/topbar/contenu
  pages/             un dossier autonome par page

Chaque page possède son propre dossier et, si nécessaire, ses fichiers :

pages/dashboard/dashboard.ts
pages/dashboard/dashboard.html
pages/dashboard/dashboard.css

Le même principe est appliqué à clients, vehicles, invoices, invoice-detail,
login et aux futures pages planning, atelier, devis et paramètres.

Remarque : le dossier frontend s'appelle actuellement « GaregePilotFront »
(avec cette orthographe). Les configurations Docker et les commandes utilisent
ce nom. Ne pas le renommer partiellement sans mettre à jour toutes les références.

7. MULTI-TENANT ET SÉCURITÉ
---------------------------

GaragePilot est multi-garages. Chaque donnée métier appartient à un garage par
garage_id. Un utilisateur appartient également à un garage.

Règle absolue : un utilisateur du garage A ne doit jamais lire ou modifier une
donnée du garage B, même s'il connaît son UUID.

Le garage_id est récupéré depuis l'utilisateur authentifié/JWT. Il ne doit pas
être accepté aveuglément depuis Angular.

Les repositories et services doivent utiliser des recherches de la forme :

findByIdAndGarageId(id, garageId)

et jamais un simple findById(id) pour une ressource métier exposée.

Les modules Client, Vehicle et Invoice appliquent actuellement ce filtrage.
Les futurs modules doivent obligatoirement appliquer la même règle.

Supabase utilise également Row Level Security sur les tables métier. L'isolation
principale de l'application reste néanmoins contrôlée dans le backend Spring,
car les appels passent par l'API et non directement par Angular.

Autres règles :

- mots de passe hachés avec BCrypt ;
- aucun mot de passe dans les DTO ;
- endpoints protégés par Spring Security ;
- JWT ajouté par l'intercepteur Angular ;
- validation backend obligatoire ;
- entités JPA jamais retournées directement ;
- erreurs gérées par un RestControllerAdvice ;
- données métier importantes désactivées plutôt que supprimées définitivement ;
- calculs financiers réalisés dans le backend avec BigDecimal ;
- aucun secret codé en dur dans les sources.

Rôles prévus : OWNER, ADMIN, MECHANIC et RECEPTION.

10. BACKEND DÉJÀ IMPLÉMENTÉ

Authentification :

  crée un Garage et son premier utilisateur OWNER ;

  vérifie les identifiants et retourne un access token JWT ;
- JwtAuthenticationFilter charge l'utilisateur ;

- SecurityConfig définit les routes publiques et protégées.

Clients :

- PUT /api/clients/{id} ;

Véhicules :

- GET /api/vehicles avec recherche et pagination ;
- GET /api/vehicles/{id} ;
- POST /api/vehicles ;
- PUT /api/vehicles/{id} ;
- DELETE /api/vehicles/{id}, qui désactive le véhicule ;
- lien obligatoire avec un client du même garage ;
- isolation par garage.

Factures :

- GET /api/invoices avec recherche et pagination ;
- GET /api/invoices/{id} pour le détail ;
- POST /api/invoices pour créer une facture et ses lignes ;
- GET /api/invoices/{id}/pdf pour télécharger la facture ;
- PUT /api/invoices/{id} pour modifier uniquement une facture au statut DRAFT ;
- recalcul backend du sous-total, de la TVA, du total, du payé et du solde ;
- lignes de type LABOR, PART, SERVICE ou OTHER ;
- statuts DRAFT, ISSUED, PARTIALLY_PAID, PAID, OVERDUE et CANCELLED ;
- contrôle du garage sur la facture et ses relations ;
- génération PDF A4 avec informations garage, client, véhicule, lignes,
  sous-total, TVA, total TTC, montant payé et solde ;
- nom téléchargé : facture-{numero}.pdf.

Gestion des erreurs :

- ApiExceptionHandler centralise les erreurs ;
- ResourceNotFoundException pour les ressources absentes ;
- BusinessException pour les règles métier ;
- format de réponse API cohérent.

16. PROBLÈMES DÉJÀ RENCONTRÉS ET SOLUTIONS
------------------------------------------

Backend tentant localhost:5432 :

Cause : variables Supabase non chargées ou ancien profil.
Solution : .env à la racine, profil supabase et application-supabase.yml.

« Impossible de charger les véhicules » :

Cause rencontrée : backend non démarré, ancienne JVM ou données non associées au
garage connecté. Vérifier le port 8080, les logs, le JWT et le garage_id.

« Impossible de télécharger le PDF » :

Cause rencontrée : Angular utilisait bien 8080, mais ce port était occupé par
une ancienne JVM IntelliJ démarrée avant l'ajout d'OpenPDF et du nouvel endpoint.
Solution : recharger Maven dans IntelliJ, arrêter l'ancienne exécution, compiler
et redémarrer le backend.

« Invalid PrimeUI License » :

Cause : providePrimeNG et @primeuix/themes initialisaient PrimeNG 22 alors
qu'aucun composant PrimeNG n'était utilisé. Solution appliquée : suppression de
ces deux dépendances et du fournisseur de thème. PrimeIcons reste utilisé. Ne
jamais masquer cet avertissement par CSS ni modifier node_modules.

API retournant 403 après vérification de l'état du garage :

Cause : JwtAuthenticationFilter accédait à Garage.active via une relation LAZY
après la fermeture de la transaction du repository. L'exception était capturée
et l'authentification effacée. Solution : UserRepository.findSecurityUserById
charge explicitement le garage avec @EntityGraph.

Code écrit sur une seule ligne :

Solution mise en place : Spotless pour Java et Prettier pour Angular. Exécuter
les commandes de formatage avant livraison.

Affichage de caractères accentués étrange dans certaines sorties PowerShell :

Il peut s'agir de l'encodage de la console, pas nécessairement du fichier. Les
PDF générés ont été contrôlés visuellement et affichent correctement les accents.
